## 本次源码核对与规划调整建议

1. **保留现有构建方式。** 上游服务实际是 Make，不是 CMake：`server/Makefile`、`config.mk` 和 `common.mk`。先复现原构建；新增 Drogon 时为 HTTP 服务引入其需要的构建方式，不将迁移整个 TCP 工程作为前置条件。
2. **修正 RAG 技术栈描述。** KBrag 当前 `.env.example:21` 默认 `Qwen/Qwen3-Embedding-8B`，README 描述 BM25 + Qwen3 Dense + RRF + Qwen3 Rerank。规划中的 bge-m3 不是当前默认方案。诊断语料的模型选择、成本与评测在阶段 5 再确定，不继承产品问答的效果数字。
3. **明确事件接口的阶段依赖。** 原计划阶段 2 提供事件查询，阶段 4 才实现异常检测。建议阶段 2 先交付 health、overview、workers、metrics；事件查询与规则一起在阶段 4 交付，避免空接口被理解成已实现。
4. **先测量再决定开销目标。** 监控前后必须使用同一环境、构建模式和负载，多轮记录吞吐及延迟。可接受开销阈值在得到新基线后、实现采集前确认，不预先承诺性能数字。
5. **已有 MCP 只是可复用入口。** 原 `epoll_mcp/server.py` 提供 Ping、文档检索、固定日志读取，不具备真实 Worker 指标和历史实验工具；不能作为新诊断模块完成的证据。

以上为本轮实施建议；其中尚未到开发阶段的选型仍可调整。

## 指标采集的设计约束，阶段 1 前细化

- 当前在线连接数和收发队列长度存在原子计数来源，但不等于已有跨进程观测接口。
- `m_onlineUserCount` 表示连接数量，不能描述成已登录业务用户数。
- 原子字段逐个读取不保证整份快照在同一瞬间一致；需定义可接受的采样语义。
- 完成请求数、CRC 失败累计、数据库等待及 Redis 耗时等需要检查插桩路径，缺失数据不能填 0 冒充实测。
- 文件快照写入不能直接放进 epoll 收发热路径；采用低频、有界的后台采样，并处理磁盘写入失败。
- 临时文件与目标文件必须处于同一文件系统，以原子 rename 发布完整快照。
- 身份需要区分服务启动轮次和 Worker 生命周期，避免 PID 重用、旧快照和计数归零造成误判。
- 数据缺失、过期、部分 Worker 采集失败和 TCP 业务不可达需要分别表示。HTTP 自身存活与 TCP 健康也应分别报告。

## NATS 类比的边界

可以借鉴客户端连接与 HTTP 监控端口分离的设计。NATS 官方资料说明监控端口独立于客户端端口：<https://docs.nats.io/learn/monitoring/monitoring-endpoints>。

本项目仍围绕既有 TCP 业务服务做观测和诊断；目前不引入发布订阅、消息路由或消息持久化需求。
