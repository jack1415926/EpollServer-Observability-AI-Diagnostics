## 结论与当前完成边界

阶段 5 已证明任务、工具、模型、持久化和网页能够贯通，也覆盖了有限的真实故障与故障隔离；**尚未证明知识库覆盖足够、检索参数适合本领域，或诊断能推广到未见过的故障**。40 项回归主要验证工程行为，不能换算成诊断准确率。

项目小，并不自动意味着不能使用 RAG；当前更具体的问题是：语料高度集中于本项目及其上游，进度记录与技术知识混合，独立案例不足，运行观测存在缺口，检索效果没有基准。即使模型能流畅引用这些资料，也可能只是在复述已经写进文档的解释。

## 2. 诊断提示词来自哪里、如何组成

目前提示词是本项目开发时直接编写在 `diagnosis/agent.py:136` 的固定 SYSTEM 字符串，**不是从语料自动生成，也不是经过专门评测选择出来的提示词**。未直接沿用 KBrag 的产品问答提示词。

固定规则主要是：只读工具；文档和日志不能改写系统指令；采集完整不代表业务健康；null 表示未知；历史资料与当前观测区分；原因只列为推测；证据不足承认无法确定根因；输出 JSON 并引用真实 E 编号。

一次诊断的实际组成（`diagnosis/agent.py:142`）：

```text
先固定执行 health、workers、events、experiments 四种读取
再以问题前 500 字符做一次知识检索
    ↓
SYSTEM 固定规则
USER = 原问题 + 初始证据 + Pydantic 生成的报告 JSON Schema
    ↓
最多两轮模型工具决策；每轮最多执行四个工具
工具说明与参数 schema 由本地代码生成，工具结果附加进消息
    ↓
追加最终指令，列明允许引用的 E 编号
单独调用模型生成 JSON
    ↓
结构校验、引用编号存在性校验、脱敏、落库
```

模型调用关闭 thinking，输出上限 4000 tokens；没有示例驱动、专家诊断检查表、提示词版本号或自动提示词优化。工具轮没有工具请求时会直接结束循环，随后仍单独请求最终报告；该轮已有的回答正文不会直接作为最终报告使用。

主要限制：

- 提示词反复提醒保守边界，但没有按症状组织“需要哪些证据才能区分哪些原因”的诊断方法。
- 每个问题都固定读四类运行资料，即使问题只是技术概念；增加成本与不相关上下文的可能性，尚未测量其影响。
- 引用校验仅保证 E 编号存在，不检查引用内容能否支持对应句子，也不检查数值、时间和实例是否真正一致。
- unknowns 必须非空，只能证明输出有此字段；不能证明模型理解了真正缺失的证据。
- 当前结论枚举只有 insufficient_evidence / possible_causes，且规则要求原因只能为推测。这是保守边界，不能据报告把根因标成已验证；将来如需“已确认根因”，应先定义证据标准。
- 实际报告未记录完整的提示词/语料发布版本、检索中间排名与分数、token 用量、provider 返回的具体模型版本或 finish_reason，复现实验与分析截断较困难。

## 3. 检索架构及与 KBrag 的差异

当前实现见 `diagnosis/retrieval.py:67`，是重新编写的简化混合检索，没有直接调用 KBrag 的 RetrievalEngine：

```text
问题
 ├─ 本地中英文分词 → BM25 前20
 └─ 远端 Qwen Embedding → L2 归一化 → NumPy 内积前20
                         ↓
              RRF：两路等权，k=60
                         ↓
                   合并前20片段
                         ↓
              远端 Qwen Reranker 前5
                         ↓
              复核源文件哈希，返回片段
```

归一化向量的 NumPy 精确内积与 IndexFlatIP 使用相同的相似度计算；它是本地向量索引，并非远端向量数据库。291 条向量本身没有要求引入更重的存储服务。

| 环节 | KBrag-V6 固定参考实现 | 本项目 |
|---|---|---|
| 知识对象 | 产品手册、章节、图片等 | 项目 Markdown 与历史技术笔记 |
| 稀疏分词 | jieba 检索分词及字符补充 | ASCII 词项与中文相邻双字片段；没有 jieba |
| Dense | 归一化 FAISS IndexFlatIP | 归一化 NumPy 精确内积 |
| 召回组织 | BM25/Dense，加逐关键词召回及原问题/语义查询路径 | 单个原始查询，两路各前20 |
| 路由 | 产品范围限制等 | 没有产品路由，也没有诊断领域路由 |
| 融合与重排 | RRF、候选池20、Qwen Rerank | 同一方法骨架及模型，参数尚未本项目调优 |
| 返回上下文 | 默认完整父章节，并保留命中片段，相关去重逻辑 | 返回最多5个窗口片段；没有父章节回填和同源邻段去重 |
| Agent | 产品技术问答的受限检索循环 | 固定运行证据采集＋最多两轮七种只读工具＋JSON报告 |

参考核对：`sources/KBrag-V6/retrieval_engine.py` 的 tokenize_mixed、_search_text_manual、_build_results 和 _rrf_merge，以及 `agent.py` 的工具循环；参考提交为 `472a69940e61fd38c70d12c727419286e24742a8`。

因此，**方法骨架与模型有明确借鉴，实现和领域流程做了裁剪，但不能说已经完成诊断领域的检索优化**。尤其前20、RRF k=60、前5是初始选择，没有本项目消融结果支持。

当前具体限制还包括：始终返回若干近邻，没有“不相关则不返回”的语义拒答机制；Rerank 分数在客户端仅校验后未向上返回；重叠片段可能占满前5；旧版本/当前版本同池检索，主要靠提示词解释优先级；截取问题前500字符可能漏掉末尾关键条件。分数阈值不能直接拍定，需根据本项目标注集校准。

## 4. 哪些数据和结构依赖本项目，可能限制充分性

项目专用接口本身合理；问题在于适用范围与证据能力是否被准确描述。

| 环节 | 当前依赖 | 限制与可能后果 |
|---|---|---|
| 文档来源 | 一个仓库及其上游，混有进度、规划、验收和故障笔记 | 重复叙述或旧结论可能被当成多个独立证据；扩展领域覆盖有限 |
| 实时身份与指标 | 自定义 Master/Worker 文件、PID/start_ticks、连接和队列 | 适用于当前服务，尚不能作为通用 Linux 服务观测接口 |
| 指标缺口 | CPU/内存、累计网络/业务计数、MySQL/Redis 内部信息未支持 | 无法仅凭队列和文档区分 CPU 忙、锁等待、DB等待、下游变慢；补文档无法生成这些事实 |
| 健康与事件 | tcp_health=not_probed；规则限采集、进程、队列 | 确认的是监控或基础观测状态，无法覆盖实际业务失败原因 |
| 实验资料 | 固定项目报告 schema，最近100条列表、按UUID比较 | 没有按症状/环境/版本检索相似实验的工具；原始资源时间线没有进入诊断 |
| 日志 | 一个固定文件的末尾64KiB/100行，实例未核验 | 无故障时间窗口/Worker过滤，可能缺失关键片段或混入旧实例 |
| 证据结构 | E编号、scope、取得时间、整段JSON摘录 | 缺少统一的观测时间窗、实体关联与结构化证据断言；取得时间不等于事件发生时间 |
| 验收样例 | 同项目故障文档、同项目注入和两份历史报告 | 主要证明熟悉场景可贯通，不能排除“答案在语料中、问题也由同一解释派生”的评测偏差 |
| 测试资源入口 | 当前脚本默认指定 artifacts/stage3-live-dvpeok8b/experiments | 新机器没有该目录时完整联调不能原样重现；需要显式外部样例参数与独立样例契约 |
| 报告校验 | JSON与编号存在性 | 可以捕获结构/引用错误，无法证明推断正确、实验可比或根因识别准确 |
