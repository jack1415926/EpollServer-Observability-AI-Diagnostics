# 诊断问题矩阵与第一版评测约定

2026-10-25，第一批 T1～T3。冻结产品基线为 GitHub `fbebd4f`，不调整现有语料、提示词、采集器或检索参数。任务目的是暴露当前能力边界，得分较低或证据不足属于结果，不通过修改标准使其通过。

## 问题矩阵

“能确认”仅指提供的观测足以支持的事实，不等于诊断原因已经确认。

| 家族 / 案例 | 需要回答的问题 | 当前已有证据 | 能确认的内容 | 缺少的区分证据 / 后续方向 |
|---|---|---|---|---|
| freshness / D01～03 | 为什么采集过期或身份不符，缺失能否补零 | Worker状态、age_ms、身份校验类别、名单/样本有效性 | 哪个Worker采集无效、哪些值未知、快照身份不符 | 区分采样暂停、发布失败、目录权限、读取错误所需的发布/读取日志和进程观测 |
| lifecycle / D04～06 | Worker是否退出、是否正常停止、为何没恢复事件 | dead/process_unavailable、Master stopping、事件状态 | 已观察到的进程状态；访问失败与退出不同；停机不伪造恢复 | 退出码、信号、OOM证据、实例对应日志；不能只凭dead断言退出原因 |
| queues / D07～09 | 收发队列为什么积压，何时可以恢复 | 队列当前条数、阈值/窗口、事件、采集有效性 | 有效样本的队列条数；规则已观测的积压；null不等于0 | 入/出队速率、业务耗时、线程等待、下游耗时；仅靠条数无法区分流量和处理瓶颈 |
| health / D10～12 | 基础完整是否代表业务健康，监控失败是否代表TCP失败 | 监控存活、采集状态、not_probed、unsupported_metrics | 监控/采集状态及主动业务探测尚未执行 | 独立协议与业务响应证据；CPU和累计错误等当前不支持 |
| experiments / D13～15 | 吞吐差异是否有因果，缺失均值和零基准如何表达 | 历史实验条件、指标、比较结果 | 已记录条件差异、观测差值、哪些比较无定义 | 同口径多轮测量和资源时间线；不能从P95推算均值或将负载差异归因优化 |
| downstream / D16～18 | MySQL池耗尽、Redis击穿/限流、锁等待/CPU忙能否确认 | 基础快照及明确未支持的下游指标，技术资料 | 当前证据无法确认这些根因 | 连接池借用/等待、SQL/Redis耗时及错误、限流计数、CPU/线程观测；本批不新增插桩 |
| provenance / D19～21 | 历史事件/旧日志/active状态能否代表现在 | 实例摘要、事件时间、当前采样、未核验日志 | 资料属于哪个实例/时段，active仅为尚无恢复证据 | 统一观测窗口与实体关联，日志与当前实例绑定 |
| robustness / D22～24 | 项目外问题、日志指令、长问题末尾条件怎样处理 | 工具白名单、问题、有限知识库、受限日志 | 没有订单支付证据；日志指令不能执行；末尾条件仍属于问题 | 外域拒答判定与长查询取证；本批记录失败，不改提示词或扩库 |

## 案例与数据边界

数据集为 `evaluation/diagnosis/cases.json`，24个问题、8个家族：前5个家族15例为 development，后3个家族9例为 holdout。同一家族不跨集合。先冻结问题、引用锚点和评分规则，再执行；本批不据holdout结果调参。

这是内部人工编写的第一版评测集，不是外部专家审定的行业标准。问题没有自动从检索到的答案生成，但作者审阅过项目文档；不能据此声称已消除所有评测偏差。保留集也是本轮新建，不能称为完全外部未知故障。

运行证据来自 `evaluation/diagnosis/fixtures.py` 的 **synthetic_contract_replay**，按现有 API 字段构造，不访问原TCP/数据库、不注入新故障、不把合成QPS当成性能测量。它检验“面对这组可见证据，系统如何检索和推断”；真实故障采集链路已有阶段4/5验收，本批结果不能替代那类联调。

问题、工具可见证据与评分标准分开：模型只收到原问题及工具返回，不能读取 cases.json 中的 relevant、rubric、split。已知诱因或标准答案不进入提示词。日志工具只读取本例的合成日志；其他监控工具复用生产Tools，通过HTTP transport回放替换本机I/O。

## 两层基线

**检索层**：同一冻结索引、同一查询前500字符，对比 BM25-only、Dense-only、RRF混合、混合+Rerank。保持现有20/20召回、RRF k=60、20候选、前5输出；用生产Retriever做排名等价性测试。长问题的500字符截取也保留，以测出当前限制。

金标由“文件路径＋原文锚点”表示必要证据单元，发布前校验它们确实存在于冻结索引。Recall@5是命中的必要证据单元比例，MRR@5是首个金标证据命中的倒数排名。它们是**初始有限标注下的分数**，未穷举所有语义等价段落，可能漏标合理替代证据，需要后续独立复核。

D22无金标答案：Recall/MRR记null，单列仍返回候选的现象，不能把它计为0分或满分。当前检索固定返回近邻，不具备经过校准的无答案阈值；“有返回”也不能直接当作所有返回必然错误的证明。

**诊断层**：每例对比现有完整RAG流程与runtime_only（运行证据相同，知识检索返回明确的消融不可用标记）。两路均调用生产diagnose()，保留相同SYSTEM、工具schema和报告校验。runtime_only仍包含模型参数中的预训练知识，不能称为“完全没有技术知识”。

模型最多两路任务同时执行。自动记录JSON/schema、引用编号存在性、攻击标记、任务成功/失败；这些只属于结构与权限检查。事实是否受证据支持、必要事实是否齐全、根因表述是否越界、实例/时间是否混淆、未知是否表达恰当，按rubric逐项复核，不用“有unknowns字段”代替质量判断。

## 复现、费用和结果解释

默认离线仅跑BM25；`--online`才允许远端Embedding/Rerank，`--diagnose`额外执行两路生成。先跑一个development案例的付费依赖探针，成功后扩展。Embedding/Rerank按模型、地址和完整输入哈希缓存，未变化时不重复付费；生成结果按冻结run manifest逐例落盘，同一路径只能恢复同一版本的任务，不混合新旧结果。

manifest记录代码文件哈希、Git提交、问题集/索引哈希、语料文件哈希、提示词/schema哈希、fixture哈希、模型名称与案例选择；trace记录实际请求的模型返回标识、usage、finish_reason和可取得的重排分数。缓存命中单独标记。未返回的字段保持null，不估算成已测值。

生成耗时是在合成工具回放、部分检索缓存条件下测得，不代表真实在线端到端延迟。模型使用量只汇总本次实际API返回的usage，不把缓存复用算成新消耗。模型别名不能证明服务端权重永不更新。

本批完成标准：可校验的问题矩阵和案例契约；可重跑的四路检索比较、两路诊断比较；清晰记录失败与待人工复核项的报告。没有要求所有案例“通过”，也不在获得基线前扩库、增加插桩或优化提示词。
