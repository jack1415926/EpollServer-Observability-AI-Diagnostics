# 压测问题定位与解决记录

> 本文保留压测过程中有复用价值的推理和 A/B 证据，不记录每次命令输出。最终性能数据以 [PERFORMANCE_VALIDATION.md](PERFORMANCE_VALIDATION.md) 为准。

## 1. 问题：新客户端单进程 QPS 约减半

### 现象

旧 Python 客户端在 12-vCPU VM 上曾报告约 1.8 万 QPS；改造后的严格客户端只有约 0.86 万。候选原因包括：

1. 当前服务端加入 MySQL、连接并发保护后变慢。
2. 完整收包、字段/CRC 校验或全量延迟记录消耗过大。
3. Python 单进程/GIL 或 Socket 超时实现成为瓶颈。
4. VMware vCPU 调度导致偶然差异。

### 先排除服务端回退

使用相同客户端交叉测试旧、新服务端：

| 服务端 | 客户端 | QPS |
|---|---|---:|
| 当前服务端 | 早期严格客户端 | 约 8552 |
| 旧服务端 | 早期严格客户端 | 约 8571 |
| 当前服务端 | 原始旧客户端 | 约 1.80 万 |
| 旧服务端 | 原始旧客户端 | 约 1.77 万 |

更换服务端几乎不改变结果，更换客户端却接近翻倍。因此 MySQL、当前连接锁和服务端版本不是这次减半的主要原因。Ping 本身也不查询 MySQL。

### 拆分客户端开销

首先只改变延迟记录方式：

| 单进程模式 | QPS |
|---|---:|
| 每请求记录延迟 | 8584 |
| 每 100 请求抽样 | 8708 |
| 不记录请求延迟 | 8598 |

三者接近，排除全量延迟数组是主要原因。

随后在同一服务和时间窗口只改变收包/校验方式，Socket 均保持 Python 3 秒超时：

| 收包与校验 | QPS |
|---|---:|
| `recv_exact` + 严格校验 | 8791 |
| 预分配 `recv_into` + 严格校验 | 8889 |
| 单次 `recv` + 严格校验 | 9052 |
| 单次 `recv` + 仅长度判断 | 9200 |
| 旧式内联热循环 + 仅长度判断 | 9741 |

完整收包、内存分配和字段校验都只有小幅影响，仍不能解释约 2 倍差距。

最后只改变连接成功后的 Socket 超时机制：

| 模式 | QPS | 安全边界 |
|---|---:|---|
| 旧式内联循环 + Python 超时 | 9741 | 有响应超时 |
| 旧式内联循环 + 阻塞 Socket | 17788 | 无响应超时，仅诊断 |
| 同窗口原始旧客户端 | 18157 | 无响应超时，校验不完整 |
| 完整收包、严格校验 + 阻塞 Socket | 16171 | 无响应超时，仅诊断 |
| 完整收包、严格校验 + Linux 内核超时 | 16099 | 有响应超时，正式方案 |

这组单变量对照锁定根因：Python `socket.settimeout()` 使用非阻塞 Socket，并为 I/O 增加就绪等待；对于 8 字节 Ping，这部分固定开销占比很高。VMware 会造成轮间波动，但同窗口旧客户端仍达到 18157，因此不能用 VM 波动解释这次减半。

## 2. 解决方案：保留超时与严格校验

最终客户端没有回退到旧脚本的不完整校验，而是：

1. 连接阶段使用 Python 超时，防止 `connect()` 无限等待。
2. 连接成功后恢复阻塞 Socket。
3. 通过 Linux `SO_RCVTIMEO`、`SO_SNDTIMEO` 设置内核收发超时。
4. 每个连接预分配 8 字节缓冲区，用 `recv_into()` 循环收满。
5. 每个响应校验包长、命令码和空包 CRC。
6. 将 `EAGAIN`/`EWOULDBLOCK` 归类为 `timeout`。

离线临时服务器已验证：响应分段仍能完整接收，错误长度/命令码/CRC会判失败，服务端不响应时内核超时会被正确分类。严格单进程从约 0.89 万恢复到约 1.61 万 QPS；相对旧客户端剩余约 10% 差距是完整校验和安全边界的可解释成本。

## 3. 问题：单进程仍不足以压满服务端

客户端增加 `--processes` 后，总并发和总请求数保持不变。探索结果为：

| 客户端进程数 | QPS |
|---:|---:|
| 1 | 约 0.86 万（修复前口径） |
| 2 | 约 2.04 万 |
| 4 | 约 3.70 万 |
| 6 | 约 5.16 万 |
| 8 | 首轮异常回落到约 3.30 万 |

1→2→4→6 的增长证明早期约 1 万主要是单 Python 进程上限。8 进程首轮的客户端 CPU 反而异常下降，不能据此判定服务器饱和，因此又进行了公平复测。

### 6 进程与 8 进程公平对照

固定服务端 CPU 0–3、客户端 CPU 4–11，使用相同内核超时、严格校验、200 并发和每轮 200 万请求：

| 进程数 | 三轮 QPS | 中位数 | p95 中位数 |
|---:|---|---:|---:|
| 6 | 53059 / 47310 / 53218 | 53059 | 6.60 ms |
| 8 | 47337 / 50726 / 49442 | 49442 | 6.75 ms |

两组各 600 万请求零失败、无应用层发送丢弃。6 进程中位数高约 7.3%，因此最终选择 6 进程；“进程数越多越快”不成立。

## 4. 最终基线与 Redis 成本

在已推送代码、干净工作树上重新测试，得到最终可引用结果：

| 模式 | QPS 中位数 | p95 | 请求结果 |
|---|---:|---:|---|
| Redis Lua 关闭 | 51873 | 6.69 ms | 600 万，零失败 |
| Redis Lua 开启，阈值 1 亿 | 27893 | 10.59 ms | 600 万，零失败 |

Redis-on 期间观测到 610 万次成功 `EVAL`，恰好对应 10 万预热和 600 万正式请求。由此可将约 46.2% 的 QPS 下降归因于当前“每个合法包同步执行一次 Redis Lua 往返”的设计，而不是限流误触发或 Redis 报错。

## 5. 能证明与不能证明的结论

能够证明：

- 单进程减半的主要原因是 Python 用户态超时 Socket，而不是当前服务端回退。
- Linux 内核超时能在保留超时和严格校验的情况下恢复大部分吞吐。
- 6 个压测进程比 8 个更适合当前同机 CPU 分配。
- 每请求同步 Redis Lua 是明确的性能成本。

不能证明：

- 5.19 万 QPS 是服务器理论上限。
- 12 vCPU 必然比 6 vCPU 快；VMware 宿主机调度未受控。
- 当前配置适合生产环境；密码安全、慢读和 sanitizer 专项仍未完成。
- 增加 120 个业务线程必然提升吞吐；线程数没有进行系统调优。

## 6. 面试复述顺序

1. 先说明看到新旧客户端 QPS 相差约一倍，没有直接修改服务器。
2. 用旧/新服务端与旧/新客户端交叉实验，排除服务端版本和 MySQL。
3. 分别关闭延迟、替换收包和降低校验，发现都只能带来小幅变化。
4. 只切换 Socket 超时机制后，QPS从约 0.97 万恢复到约 1.78 万，锁定根因。
5. 用 Linux 内核超时替代无超时阻塞，在严格校验下达到约 1.61 万。
6. 再用多进程、CPU亲和性和三轮中位数建立最终 Redis-off/on 对照。

这条证据链比单独背诵“QPS约5.2万”更重要。
