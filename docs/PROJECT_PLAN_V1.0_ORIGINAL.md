# EpollServer 可观测性与智能故障诊断系统

**项目技术规划书 V1.0**

## 一、项目概述

### 1.1 项目名称

EpollServer 可观测性与智能故障诊断系统

英文暂定：EpollServer Observability & AI Diagnostics

### 1.2 项目定位

基于现有 Linux C++ 高并发 TCP 服务器，构建一套集**运行监控、状态采集、性能实验管理、异常检测与 RAG 辅助故障诊断**于一体的后端系统。

系统采用类似 NATS 的数据面与控制面分离设计：

- **业务面：** 原 EpollServer 继续使用自定义二进制 TCP 协议，处理注册、登录、用户查询等现有业务。
- **控制面：** 新增独立 Drogon HTTP 服务，提供服务器运行状态、性能指标、历史实验和诊断任务接口。
- **智能诊断：** 复用 KBrag-V6 的部分 RAG 与 Agent 能力，结合实时指标、日志、技术文档和历史实验，辅助排查问题。
- **展示层：** 提供简洁的 Web 监控与诊断界面，方便查看运行状态、历史记录及分析报告。

项目不追求替代 Prometheus、Grafana 等完整监控平台，而是围绕现有 C++ TCP 服务构建具有可验证工程价值的可观测性与诊断能力。

### 1.3 项目目标

1. 保留原有 TCP 网络框架和业务功能。
2. 为 C++ 后端增加标准 HTTP 监控与管理接口。
3. 实现 Master-Worker 多进程运行数据的可靠采集和汇总。
4. 支持服务器性能测试结果的保存、查询和对比分析。
5. 支持基础异常检测和故障事件记录。
6. 使用 Agent 工具调用与 RAG 检索辅助故障分析。
7. 建立功能测试、性能测试和异常恢复验证体系。
8. 最终形成可以独立演示、维护和解释的完整项目。

## 二、整体系统架构

### 2.1 技术栈

| 模块 | 采用技术 |
|---|---|
| TCP 业务服务器 | C++17、Linux、epoll LT、Reactor |
| 并发模型 | Master-Worker、业务线程池 |
| 自定义协议 | 现有 8 字节包头 + 可变长度包体 |
| HTTP 监控服务 | C++17、Drogon |
| 运行状态采集 | C++ 统计模块、原子计数器、跨进程状态快照 |
| 业务数据 | 现有 MySQL、Redis |
| 监控历史与实验记录 | MySQL 独立监控表 |
| RAG 检索 | Python、BM25、bge-m3、FAISS、Rerank |
| AI 编排 | 受约束 Agent Loop、Tool Calling |
| 前端展示 | 简洁 Web Dashboard |
| 构建与测试 | CMake、自动化脚本、功能与性能测试 |

### 2.2 服务划分

**模块 A：EpollServer（已有，增量改造）**

负责原有 TCP 业务，并新增内部运行指标采集能力。

**模块 B：Drogon HTTP Monitor（新增）**

作为独立 C++ HTTP 服务，负责提供监控 API、历史实验接口及诊断任务入口。

**模块 C：Metrics Collector（新增）**

负责采集各 Worker 的指标、汇总状态、识别数据过期及部分 Worker 不可用的情况。

初版使用本机状态快照作为跨进程数据交换机制。Worker 周期性写入本进程指标，使用临时文件加原子重命名，避免 Drogon 读取不完整数据；Master 维护当前 Worker 名单。后期仅在有明确需求时再改为 Unix Domain Socket 等 IPC 机制。

**模块 D：AI Diagnostic Service（新增，复用已有 Python 代码）**

复用 KBrag-V6 的检索算法和部分 Agent 编排能力，但建立独立的服务器运维知识库及诊断工具，不直接复用产品手册问答提示词。

Drogon 负责对外 HTTP 接口，Python 服务负责内部 AI 推理和知识检索。初版保留 Python 内部调用接口，避免用 C++ 重写 FAISS、Embedding 和 Agent 核心。

**模块 E：Web Dashboard（新增）**

提供状态展示、性能实验对比和 AI 诊断操作界面。

### 2.3 核心原则

- TCP 业务与 HTTP 监控不互相转换，也不重复实现业务逻辑。
- HTTP 和 AI 故障不影响 TCP 的正常收发包。
- 运行指标通过确定性程序获取，不由 LLM 猜测。
- RAG 主要检索技术知识和历史经验，不承担实时数据库的职责。
- 全部敏感管理接口默认只允许本机访问，并实施鉴权。
- 优先增量修改，避免重构原有 epoll 网络核心。

## 三、核心功能模块

### 模块 1：原 TCP 业务服务器保留与验证

**现有功能保留：**

- TCP 建立连接与断开连接。
- 自定义包头解析和 CRC32 校验。
- Ping。
- 注册与登录。
- 用户信息查询。
- MySQL 连接池。
- Redis 缓存及限流。
- Master-Worker 和业务线程池。
- 现有连接回收、超时及退出机制。

**新增要求：**

- 整理现有业务与运行状态相关的统计数据。
- 为重要请求和异常增加结构化计数。
- 提供 Worker 生命周期状态。
- 保证监控采集不会阻塞网络 I/O。
- 对原有 TCP 功能执行回归测试。

**验收：** 新增 HTTP 监控服务后，原有 TCP 客户端及业务测试继续通过；服务器性能变化应有测试记录。

### 模块 2：服务器运行指标采集

**2.1 进程级指标**

- Master PID、运行时间。
- Worker PID、启动时间、存活状态。
- Worker 启动、退出及重启记录。
- 每个 Worker 的 CPU、内存使用情况（通过系统指标采样）。

**2.2 网络指标**

- 当前 TCP 连接数。
- 累计接受连接数。
- 累计关闭连接数。
- 累计接收与发送消息数。
- 无效包、CRC 错误等异常计数。
- 收发队列积压情况。

**2.3 业务线程池指标**

- 线程池线程数。
- 待处理任务数。
- 已完成任务数。
- 拒绝或丢弃任务数。
- 队列历史峰值。
- 可测得的任务处理耗时。

**2.4 数据库及缓存指标**

- MySQL 连接池当前占用情况。
- 连接获取等待及超时次数。
- Redis 调用次数、错误次数。
- Redis 限流拒绝数量。
- 关键操作耗时统计。

上述字段应逐项核实已有源码是否具备数据来源。无法准确采集的指标不得返回伪造数值。

**2.5 跨进程指标要求**

每份 Worker 快照必须包含：

- Worker 标识、PID、启动时间。
- 采集时间与快照版本。
- 累计计数及当前状态。
- 指标采集是否成功。

汇总时应处理 Worker 重启、进程退出、计数器归零、快照过期与部分采集失败等情况。

**验收：** 能准确获取多 Worker 状态；单个 Worker 异常退出时不会把旧数据当成当前状态。

### 模块 3：Drogon HTTP 监控接口

第一版 API 建议：

| 接口 | 功能 |
|---|---|
| `GET /api/v1/health` | 查询监控服务及 TCP 服务健康状况 |
| `GET /api/v1/overview` | 查询服务器整体状态 |
| `GET /api/v1/workers` | 查询各 Worker 运行状态 |
| `GET /api/v1/metrics` | 查询网络、队列、线程池等指标 |
| `GET /api/v1/events` | 查询异常事件 |
| `GET /api/v1/experiments` | 查询历史性能实验 |
| `GET /api/v1/experiments/{id}` | 查询单次实验详情 |
| `POST /api/v1/experiments/compare` | 比较两组实验结果 |
| `POST /api/v1/diagnoses` | 提交诊断任务 |
| `GET /api/v1/diagnoses/{id}` | 查询诊断状态与报告 |

**API 实现要求：**

- 使用标准 JSON 返回结构。
- 包含时间戳、错误码和数据有效性状态。
- 超时、异常、指标缺失时返回明确错误。
- 支持基本身份认证和访问控制。
- 限制请求体长度、调用频率和并发数量。
- HTTP 服务只读访问运行指标，不直接修改 TCP 业务状态。

初版不提供远程执行 Shell、重启 Worker、动态修改服务器配置等高风险管理操作。

### 模块 4：Web 监控界面

提供四个主要页面。

**4.1 服务器总览**

展示 TCP 服务健康状态、Worker 数量、连接数、消息速率、队列积压及最近异常事件。

**4.2 Worker 与资源监控**

展示各 Worker 的运行情况、CPU、内存、连接数量、线程池队列和异常统计。

**4.3 性能实验中心**

查看历史压测记录，对比 QPS、P95 延迟、错误率和资源占用情况。

**4.4 智能诊断中心**

用户输入故障问题，选择运行实例或历史实验，查看 Agent 生成的诊断结论、证据和验证建议。

界面使用简洁的 Web 实现，不引入 Qt；界面只需要清楚展示数据，不以复杂的视觉设计为主要目标。

### 模块 5：性能实验记录与对比分析

**主要功能：**

- 导入现有压测脚本产生的结果。
- 记录压测命令参数、并发量、持续时间、代码版本和运行配置。
- 保存 QPS、平均延迟、P95、成功数、失败数。
- 将实验与当轮资源指标关联。
- 支持选择两次实验比较差异。
- 形成结构化实验报告。

**初始实验场景：**

1. Redis 限流开启与关闭。
2. 不同并发数下的吞吐与延迟。
3. 不同线程池配置下的性能变化。
4. MySQL 连接池竞争和获取超时。
5. 慢客户端、异常断开及请求积压。

实验应采用可重复的条件和多轮测试，不能将不同硬件或不同测试脚本得出的数据直接当作公平对比。

历史实验摘要、配置和诊断报告可持久化到独立的 MySQL 监控表；原始日志及大体积采样数据可以保留在受控文件目录中。

### 模块 6：异常检测与事件记录

在 AI 诊断之前，先提供确定性的基础异常检测。

**候选规则：**

- TCP 服务不可用。
- Worker 非预期退出。
- 指标采集超时或数据过期。
- 队列积压超过配置阈值。
- 业务错误率异常上升。
- 数据库连接池获取超时。
- Redis 连接或调用异常。
- 性能实验相较基准出现显著回归。

规则应具备明确阈值、检测窗口和去重机制，避免同一异常每秒产生大量重复事件。

异常事件应保存触发时间、相关实例、观测值、阈值及处理状态。

**验收：** 能通过可控故障实验触发相应事件，恢复后状态正确更新。

### 模块 7：Agent 与 RAG 智能诊断

**7.1 目标**

让开发者使用自然语言查询和分析服务器故障，并得到基于证据的回答。

例如：

- 为什么这轮压测吞吐下降？
- 当前是否存在线程池任务积压？
- Redis 限流机制可能影响哪些请求路径？
- 某个 Worker 退出后，哪些日志和指标值得检查？
- 当前表现与历史哪次性能实验相似？

**7.2 RAG 知识库**

知识来源包括：

- EpollServer 架构文档。
- 网络协议和收包状态机说明。
- Master-Worker、线程池与连接生命周期文档。
- MySQL、Redis 实现说明。
- 历史性能实验结论。
- 经确认的故障排查记录和技术笔记。

不将高频实时指标直接写入向量索引。实时指标通过工具获取；确认过的故障案例可以离线更新到知识库。

**7.3 可复用的 KBrag 能力**

优先复用：

- 文档切分和索引构建方法。
- BM25 + Dense 混合召回。
- RRF 融合与 Rerank。
- Agent Loop 的受约束工具调用思想。
- 请求超时、异常处理和日志追踪机制。

需要重新设计：

- 服务器故障分类与提示词。
- 检索语料及相关评分配置。
- 运行状态查询工具。
- 历史实验查询工具。
- 诊断结果结构化输出。
- 诊断回答质量评测。

原 KBrag 产品手册问答保持独立，不直接破坏已有业务。

**7.4 Agent 工具**

建议提供：

| 工具 | 功能 |
|---|---|
| `get_server_health` | 获取服务器健康状态 |
| `get_worker_metrics` | 查询 Worker 指标 |
| `get_recent_events` | 查询近期异常事件 |
| `read_server_logs` | 受限读取相关日志 |
| `query_experiments` | 查询历史性能测试 |
| `compare_experiments` | 比较实验结果 |
| `search_technical_docs` | 检索技术文档与已确认案例 |

初版可使用受限 Python 工具适配器，后续按需要扩展现有 stdio MCP 工具集。

**7.5 诊断输出结构**

每次诊断包含：

1. 用户问题与诊断对象。
2. 已确认的运行事实。
3. 检索到的文档和历史案例。
4. 可能原因及其证据。
5. 尚未确认的假设。
6. 建议的后续验证步骤。
7. 诊断状态及相关来源引用。

当证据不足时，明确说明无法确定根因。

**7.6 长任务处理**

Agent 诊断可能需要较长时间，因此不能阻塞 Drogon 的网络事件循环。

HTTP 提交诊断任务后返回任务 ID，客户端通过查询接口读取任务状态或最终结果。

需要实现并发限制、任务超时、错误处理、过载拒绝和结果保留期限。

**7.7 诊断效果验证**

准备一组带有预期证据和已知诱因的故障测试案例，检查：

- 工具数据是否正确。
- 证据引用是否真实。
- 是否混淆历史数据与当前数据。
- 是否把推测描述为事实。
- 能否正确承认证据不足。
- AI 不可用时系统是否正确降级。

### 模块 8：日志、安全和可靠性

**日志管理：**

- 统一日志时间、级别和事件类别。
- 尽可能关联请求 ID、Worker ID 和实验 ID。
- 支持限定时间范围的日志查询。
- 避免无界读取日志文件。
- 对账号、密码、令牌等敏感信息进行脱敏。

**安全要求：**

- HTTP 监控服务默认仅绑定 `127.0.0.1`。
- 远程访问必须配置合理的身份验证和安全传输。
- AI 工具默认为只读，不允许任意命令执行。
- 管理服务不得通过 HTTP 暴露原有业务数据库凭据。
- 原 TCP 登录和密码处理的已有安全问题应单独修复，不将不安全的认证机制直接复用于监控管理。

**可靠性要求：**

- Drogon 崩溃不应导致原 TCP 业务退出。
- Python RAG 超时不应阻塞监控查询。
- 数据库不可用时仍尽可能提供实时健康状态。
- Worker 退出后过期指标不得被误判为正常。
- 启停和异常恢复行为应具备自动化测试。

## 四、数据库与数据管理

新增独立的监控数据模型，不直接修改原有用户业务表的语义。

建议设计以下逻辑数据表：

| 数据表 | 主要内容 |
|---|---|
| `monitor_experiment` | 性能实验元数据与配置 |
| `monitor_experiment_metric` | 实验统计和采样指标 |
| `monitor_event` | 异常事件与状态 |
| `diagnosis_task` | AI 诊断任务与执行状态 |
| `diagnosis_report` | 诊断结果和证据来源 |

实时 Worker 指标主要由采集模块获取和汇总，不要求每秒将全部细粒度指标写入 MySQL。

MySQL 用于保存有长期价值的历史数据；高频监控快照设置保留期限，防止无限增长。

## 五、代码组织建议

保留两个原仓库，以增量开发为主。

**Learn_EpollServer：**

- `server/`：现有 TCP 服务，补充统计能力。
- `monitor/collector/`：新增运行指标采集与汇总。
- `monitor/http/`：新增 Drogon HTTP 服务。
- `monitor/web/`：监控界面。
- `monitor/tests/`：监控及性能验证脚本。
- `docs/`：架构、接口、实验与部署文档。

**KBrag-V6：**

保留现有产品问答系统，并新增相对独立的诊断适配模块或独立 Python 服务，复用适合的检索代码与 Agent 方法。

具体文件目录应根据实际代码结构确定，不机械照搬建议目录。

## 六、开发实施阶段

### 阶段 0：基线确认

- 整理原 EpollServer 的构建与启动过程。
- 运行已有 TCP 业务测试。
- 保存当前性能基线。
- 明确指标采集的数据来源和线程安全要求。
- 固定已有项目的主要架构边界。

**阶段完成标志：** 原系统功能和性能有可复现的基准。

### 阶段 1：运行指标采集

实现 Worker 统计、Master 状态、快照输出、读取和汇总。

**阶段完成标志：** 不依赖 HTTP，也能准确得到结构化运行快照。

### 阶段 2：Drogon HTTP 监控

建立独立 Drogon 服务，实现健康检查、整体状态、Worker、指标和事件查询。

**阶段完成标志：** HTTP 返回真实数据，监控失效不会影响 TCP 业务。

### 阶段 3：Web 监控与性能实验

开发简洁监控页面，支持指标查看、历史实验查询和结果对比。

**阶段完成标志：** 可以从网页观察服务器，并复现、比较至少两组性能实验。

### 阶段 4：基础异常检测

实现确定性异常规则、事件记录和查询。

**阶段完成标志：** 通过可控故障可以触发、记录和恢复事件状态。

### 阶段 5：RAG 与 Agent 诊断

建立服务器技术知识库，接入查询工具，实现诊断任务管理和带证据的分析输出。

**阶段完成标志：** 能对真实或可复现的故障提供有证据的分析，且正确处理未知与超时情况。

### 阶段 6：系统测试与交付

- TCP 功能回归。
- HTTP 接口测试。
- 多 Worker 状态一致性测试。

## 七、完整项目的验收标准

项目完成时应达到以下标准：

**业务完整性：** 原有 TCP 功能正常，HTTP 监控和 AI 诊断可独立工作。

**监控可信性：** 能准确获取主要运行状态，正确处理多 Worker 汇总、数据过期与采集失败。

**实验可复现：** 至少具备多组可重复性能实验，能够比较结果并关联运行证据。

**诊断可信性：** AI 能综合真实指标、日志和文档，明确区分事实、推测和建议。

**故障隔离：** Drogon、数据库或 AI 服务出现故障时，系统不应因此破坏原 TCP 网络服务的基本运行能力。

**安全与稳定性：** 敏感接口受到保护，日志经过脱敏，关键异常路径具备测试覆盖。

**可维护性：** 提供系统架构图、模块说明、API 文档、部署说明和测试报告。

- Qt 完整桌面客户端。

- 在线动态更新全部向量索引。

- 完整的分布式集群监控平台。
- 大规模微服务治理、消息队列和 Kubernetes。
- 没有明确需求的复杂权限管理平台。

## 十、最终项目价值

项目的核心成果不是简单地把 Drogon 和 RAG 接入 EpollServer，而是：

**将原有 Linux C++ 高并发 TCP 服务器扩展为同时具备业务通信、HTTP 可观测性、性能实验分析和 AI 辅助诊断能力的完整后端系统。**

工程重点包括：

- epoll 与线程池架构的保留和演进。
- Master-Worker 多进程状态采集与汇总。
- C++ HTTP 服务设计及故障隔离。
- 运行指标采集对性能的影响评估。
- 历史性能实验管理。
- Agent Tool Calling 与 RAG 证据检索。
- 长任务管理、超时控制和服务降级。
- 功能测试、性能测试与故障恢复验证。

**这是一份目标范围完整的项目规划书，并不意味着所有模块必须在同一次迭代中完成。各阶段应分别交付可运行、可测试的结果。**
