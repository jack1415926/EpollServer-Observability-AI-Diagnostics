## 后续监控开销对照使用的多进程基线

- 服务端固定 CPU 0–3，客户端固定 CPU 4–11；本机 loopback，端口 18080，客户端源地址 `127.0.3.1`。
- 客户端 6 进程，总并发 200，每连接 10000 次 Ping，每轮 200 万请求。
- `receive-mode=into`、`validation-mode=strict`、`socket-mode=kernel-timeout`、`timeout=5`。
- 延迟每 100 个请求抽样一次；P95 中位数指三轮各自抽样 P95 的中位数，不是合并全部请求后的 P95。
- Redis Lua 开启，窗口 60 秒，阈值 100000000；保留同步 Redis 调用开销，不以限流拒绝为负载目标。
- 使用临时配置、`Daemon=0`，未修改日常配置；预热 10 万请求，正式三轮间各等待 1 秒。
- 原有 `performance_sampler.py` 包裹每轮客户端执行，采集结果写入 `resources-*.json`。

## 解释边界与下一步

这是当前 VMware、同机 Debug Ping 条件下的参考基线，不代表业务接口吞吐或理论容量。旧项目 Redis-on 的 27893 QPS 来自另一环境与测试批次；OS、Python、编译器等已变化，不能将本次数字与其差额描述为代码优化收益。

阶段 0 的 TCP 基线准备收尾。下一批限定为 Worker 进程身份、当前连接数和队列长度的基础快照；其余指标和 Master 汇总分批交付。监控开销实验应复用本组负载口径，同时保留对照版本和配置，避免用不同负载或不同 Redis 模式判断开销。
