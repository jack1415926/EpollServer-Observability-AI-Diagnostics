# 开发流程与经验

2026-10-24，根据阶段 3 复盘建立，适用于后续阶段。事故事实保留在 [开发问题记录](DEVELOPMENT_ISSUES.md)，功能与验收边界见对应阶段文档。本页规定后续实施顺序，检查通过后在已授权范围内继续推进，不增加逐项用户审批。

## 1. 开发前先验证关键依赖

- 从当前阶段目标确定最小交付范围及完成标准，先检查工作树，保留用户已有修改和本机配置。
- 对本次实际涉及的依赖核实版本、头文件/动态库路径、认证插件、运行账号权限、临时目录空间及沙箱执行限制；不重复检查无关依赖。
- 数据库先验证连接，再在已授权的监控表或私有测试实例中完成“一条真实报告写入→读回”。缺少 CREATE 权限时准备管理员建表 SQL 或使用隔离实例，不向业务账号追加权限。
- 使用一份已有真实压测结果和匹配的资源文件验证导入。检查实际字段、短提交号、缺失均值、采样模式和计数关系；不要只依靠新造的理想样例。
- 遇到库行为与预期不符时，先做最小探针，必要时核对已安装版本的实现，再扩大联调。阶段 3 的 Drogon 引号解析和 MariaDB 插件路径问题按版本处理，不推广为所有版本都如此。

**进入下一步的依据：** 关键依赖可用、真实样例能贯通最小链路，剩余不确定项及处理办法明确。连接或字段契约未打通时，先修复这条链路；可并行推进不依赖它的工作。

## 2. 先验证测试资源能安全退出

启动私有数据库、TCP 或 HTTP 常驻实例前，先确定资源归属、退出方式、超时及失败保留策略。至少验证正常退出、启动失败和清理失败时的行为，再运行完整压测或长驻联调。

清理顺序必须是：

1. 记录本次创建的进程对象、PID/启动身份、端口和目录，操作前复核归属；进程组操作只限本次自行创建的隔离进程组。
2. 先请求正常退出；私有 MySQL 使用其管理员连接执行 SHUTDOWN。
3. 等待退出并检查状态，确认子进程回收、相关端口释放。
4. 只有确定不再使用目录后，才能删除数据和配置；必要的脱敏日志先归档。

进程仍存活或状态无法确认时，保留数据目录与恢复信息，并使该清理检查失败。禁止让 TemporaryDirectory、析构函数或 finally 无条件删除仍在使用的数据库目录。保留目录中如有凭据，应限制访问并在后续安全清理。

长驻测试需明确数据/日志预计占用、可用空间和退出条件。日志异常增长或配额不足时，暂停新增相关实例，先定位资源生产者。不要清空未知 `/tmp` 文件、删除活动数据目录、批量停止同名服务，或为完成测试修改全局安全策略。

信号或文件操作返回 EPERM/EACCES 时，区分沙箱限制、文件权限和系统安全策略；不据一条错误猜测 sudo 必然有效。需要管理员介入时，提供已核验的目标身份、失败命令与错误、影响范围及具体操作。对未查明的原因保持明确的不确定性。

## 3. 分开压测、API 与页面验收

- 先完成一个最小可验收增量，再扩大实现。新测试脚本先运行最小场景，检查参数、返回值、失败传播及清理路径。
- 压测负责生成原始结果和运行条件；数据库/API 验收负责消费结果；浏览器验收复用已就绪的服务。各部分应有独立重跑入口。
- 修复 UI、导入器或数据库逻辑时，优先复用已有负载产物。现有入口为 `run_monitor_experiments.py` 生成数据，`test_stage3_live.py --reports /path/to/existing-experiments` 复用数据联调。
- 复用数据时保留其原始版本、配置、时间、采样方式和哈希，不改写为当前代码的新测量。服务端业务、客户端负载、采样逻辑或运行条件改变时，按受影响范围重新测量。

## 4. 用最小失败定位问题，再选择回归范围

- 记录当前可复现的失败命令、退出码和最短脱敏错误，区分产品代码错误、验收脚本错误和环境限制。
- 每次围绕一个影响当前失败的因素修改，先重跑最小用例，成功后再接回相关联调。不要在连接失败时反复重跑压测或浏览器。
- 每个相关验收入口在阶段收尾执行；通过后仅在新增修改、失败或未消除疑点时重跑适当范围。涉及协议、热路径或跨资源生命周期的修改，需要覆盖相应集成与退出行为。
- 已确认不可用的执行方式不反复盲试。合理合并独立的只读检查，沿用适当的已授权执行方式，依赖操作保持顺序；权限请求必须对应具体操作。
- 功能链路稳定后再集中检查完整页面、窄屏、可访问性和截图；基础样式可读性在实现时一并考虑。

## 5. 进度、交付与复盘

进度更新说明已完成的功能、已通过的验证、当前失败点及影响范围、下一步将验证什么。新出现的资源或清理问题及时说明，不用反复“正在测试”代替状态。

交付前核对并记录：

- 功能范围、实际通过的检查，以及尚未验证的内容。
- 原始产物、运行条件和本次代码状态；区分历史证据与新测量。
- 本次创建的进程、端口、目录和临时凭据的清理情况；原服务和业务数据是否受到影响。
- 功能完成、正式数据库初始化、部署和性能开销评估分别是什么状态。
- 已解决故障的原因、修复及验证；未查明的根因不写成确定结论。

本次复盘的核心教训是：先验证真实依赖和数据链路，先证明测试资源可退出，再扩大实现与验收。50 项合并回归约 27 秒是阶段 3 的实际记录；本次额外耗时主要发生在环境排障、清理事故恢复和重复联调，不能据此给未来任务编造工时比例或承诺时限。
